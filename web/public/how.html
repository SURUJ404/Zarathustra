How it works

One pipeline, eight crates

Zarathustra is a layered Rust workspace. Each layer owns one concern, so the IR stays portable, the prover stays swappable, and security analysis can inspect the whole stack.

Workspace crates

CrateRole
astra_irCore IR: AST, R1CS, Plonkish-first Constraint kinds. Free of proof crypto so it's portable across backends.
astra_frontendZara lexer/parser, span-aware errors, LSP hook, browser-native WASM bindings.
astra_codegenLowers Zara to R1CS + witness; defines the Backend trait.
astra_proverProof-system registry: ark-groth16 (default) + hand-rolled reference (legacy).
astra_stdlibVersioned gadget library (hash / signature / commitment / snark / primitive).
astra_publishVerifier export: EVM, Starknet, WASM, Aleo, JSON test vectors.
astra_securityStatic analyzers: signal flow, CEI/reentrancy, pattern checks (CIR-001..006, SOL-001..006).
astra_cliThe astra binary — a thin clap interface over the layers.

Frontend & WASM

The browser experience shares the same engine. astra_frontend compiles to wasm32-unknown-unknown and ships as web/public/pkg/astra_frontend_bg.wasm. The playground (playground.html) compiles Zara in-browser when the WASM bundle is present, otherwise falls back to the /api/* backend on Vercel.

  • Compile — native in the browser via WASM, or via the API.
  • Prove / verify — require the backend (Groth16 isn't WASM-safe yet).

Ship the site

The site is static HTML in web/public/. GitHub Pages serves it directly from the repo (see pages.yml below); the same folder is also served by Vercel for the interactive playground + API.

CI reference

Everything runs through GitHub Actions

Four workflows in .github/workflows/ enforce quality, ship docs, deploy the site, and publish releases. Every code path is gated.

ci.yml — fmt + clippy + test + self-audit

.github/workflows/ci.yml
Runs on: push to main · every pull request
  • check — matrix on ubuntu-latest + windows-latest: cargo fmt --check, cargo clippy --workspace --all-targets -- -D warnings, cargo test --workspace.
  • audit-self — builds the release CLI then runs astra audit --deny high against every crate (astra_ir … astra_cli).

pages.yml — deploy GitHub Pages

.github/workflows/pages.yml
Runs on: push to main touching web/public/**, docs/CLI.md, or this workflow
  • Configures GitHub Pages, uploads web/public as the static site artifact, and deploys it.
  • Concurrency group pages with cancel-in-progress: false so overlapping pushes queue instead of racing.

website.yml — build CLI + self-audit + deploy Vercel

.github/workflows/website.yml
Runs on: push to main touching web/**, api/**, package files, Vercel config, any astra_* crate, or .github/**
  • Builds the astra binary for Linux and copies it into api/astra (the backend the playground talks to).
  • Runs the same astra audit --deny high self-audit gate as CI.
  • Deploys to Vercel using ZARATOKEN + ORGID secrets.

release.yml — cross-platform release binaries

.github/workflows/release.yml
Runs on: tag push v*
  • build — matrix: linux-x86_64, windows-msvc, macos-x86_64. Compiles astra_cli with --locked and archives each binary.
  • publish — downloads all three archives and creates a GitHub Release with generated notes.

Run it locally

Mirror CI on your machine

These are exactly the commands the CI runs, so green locally means green in the pipeline.

$ cargo fmt --all -- --check
$ cargo clippy --workspace --all-targets -- -D warnings
$ cargo test --workspace
$ cargo build --release --locked
$ ./target/release/astra audit --deny high astra_ir astra_frontend astra_codegen \
       astra_prover astra_stdlib astra_publish astra_security astra_cli

Try the full pipeline

$ astra prove setup -p 8 -r 3,5 examples/sum.zara
$ astra prove prove -p 8 -r 3,5 examples/sum.zara
$ astra prove verify -p 8 -r 3,5 examples/sum.zara
∞  PROOF VERIFIED
