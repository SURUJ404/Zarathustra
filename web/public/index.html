Overview #

Zarathustra is a zero-knowledge proof toolkit written in Rust. Its goal is broad feature parity with — and eventually to overtake — ZoKrates. You write circuits in the Zara language; the toolchain compiles them to a constraint system (R1CS), performs a trusted setup, generates a Groth16 proof, and verifies it honestly.

Everything is honest-by-default: the verifier loads your real keys and proof files and checks the public inputs bound into the proof. Nothing is stubbed or assumed.

What's Included #

Zara language

Imperative, typed, assert-based circuit DSL with span-aware diagnostics.

astra CLI

prove, audit, deploy, publish — the whole toolkit at one command.

Security scanner

Static analyzers for circuits and Solidity verifiers with a CI gate.

Publishing

Export JSON test vectors and target verifier platforms honestly.

The Rust workspace is split into focused crates: astra_ir (IR), astra_frontend (parser/LSP/WASM), astra_codegen (lowering), astra_prover (proof backends), astra_stdlib (gadgets), astra_publish (verifier export), astra_security (analyzers), and astra_cli (the binary).

Quick Start #

Build the workspace and run the full pipeline on the example circuit:

$ cargo build --workspace
$ astra prove compile -p 8 -r 3,5 examples/sum.zara
$ astra prove setup   -p 8 -r 3,5 examples/sum.zara
$ astra prove prove   -p 8 -r 3,5 examples/sum.zara
$ astra prove verify  -p 8 -r 3,5 examples/sum.zara
✓ PROOF VERIFIED

The Zara Language #

Zara is a small, readable language for expressing circuit constraints. Functions take field parameters and return values; you assert relationships that must hold.

// Prove you know x, y such that x + y == sum
def main(field public sum, field private x, field private y) -> field {
    assert(x + y == sum);
    return 1;
}

Key points:

  • Types: the only primitive type today is field.
  • Public / private: mark inputs as public (revealed) or private (hidden in the proof).
  • assert: the constraint x + y == sum is what the prover must satisfy.
  • Diagnostics: parse and compile errors carry source spans.

Proof Pipeline #

All pipeline commands operate on a .zara source file and write artifacts into the current working directory.

compile — circuit + witness

Parses the source, lowers it to R1CS, evaluates the witness, and prints the circuit summary.

$ astra prove compile -p 8 -r 3,5 examples/sum.zara

setup — generate keys

Runs the trusted setup (CRS) and writes pk.json (proving key) and vk.json (verifying key). Defaults to ark-groth16 over BLS12-381.

$ astra prove setup -p 8 -r 3,5 --backend ark-groth16 examples/sum.zara
  Wrote pk.json, vk.json

prove — generate a proof

Builds the Groth16 proof and writes proof.json, binding the public inputs into it.

$ astra prove prove -p 8 -r 3,5 examples/sum.zara
  Saved to proof.json

verify — check the proof

Loads vk.json and proof.json and verifies against the public inputs bound into the proof. Exit status is 0 for a valid proof, 1 if it is rejected or tampered.

$ astra prove verify examples/sum.zara
✓ PROOF VERIFIED
Backends. Use --backend legacy to select the hand-rolled reference implementation instead of the default ark-groth16.

Security Audit #

Scan circuits and smart contracts for vulnerable patterns, and fail CI when findings exceed a severity threshold.

$ astra audit .
$ astra audit --format json -o audit.json .
$ astra audit --deny high .

The scanner runs signal-flow analysis (unconstrained public inputs), CEI / reentrancy checks for Solidity, plus pattern-based checks (CIR-001…006, SOL-001…006).

Publishing #

Export artifacts for target platforms. Today jt writes real JSON test vectors from your proof and verifying key:

$ astra publish -t jt
publish: wrote zara_test_vectors.json
  curve:    bls12-381
  protocol: groth16

The evm target honestly refuses BLS12-381 (no Ethereum pairing precompile for it) rather than emitting an invalid contract; starknet, wasm, and aleo are not yet implemented.
